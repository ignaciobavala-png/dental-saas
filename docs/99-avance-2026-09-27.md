## Qué se pidió

Flujo completo: página del SaaS ("Evolución Dental") → crear cuenta → panel
del consultorio. Más: sección en el panel para editar la landing propia,
tour de onboarding no intrusivo, panel como PWA (el doctor lo usa desde el
celular), y voz (STT/TTS) en el asistente, "en lo posible".

Decisiones tomadas junto al usuario (recomendadas por mí, aprobadas):
backend real (no mock) implementando H1+H2 del roadmap ahora; PWA nivel
instalable + offline básico; voz con Web Speech API nativa del navegador,
sin infraestructura nueva.

## Qué se construyó

### `packages/core` (antes vacío, `export {}`)
- `TenantContext` branded + `createTenantContext()`, `TenantDb` (list/get/
  insert/update/remove/count/scoped) sobre el registro `TENANT_TABLES`.
- Repos de plataforma (`users`, `clinics`, `memberships`, `sessions`,
  `domains`).
- Auth propia: `hashPassword`/`verifyPassword` (PBKDF2 vía Web Crypto,
  100k iteraciones) y sesión por cookie (`createSession`/`verifySessionToken`/
  `destroySessionToken`, token hasheado con SHA-256 antes de guardar).
- `Capability`/`can(ctx, cap)` — autorización por capacidad, no por rol
  comparado a mano.
- Migraciones `0001_platform.sql` / `0002_tenant_core.sql` (SQL literal de
  docs/03), incluyendo el índice anti doble-reserva (`ux_appt_slot`, único
  parcial sobre `appointments` con status pending/confirmed).

**Desviación de arquitectura respecto a docs/08 (ADR A2):** ese doc
recomienda Better Auth sobre D1. Implementé sesión propia porque docs/03 §2
y docs/10-seguridad.md ya especifican el esquema completo (`sessions` con
`token_hash`, cookie httpOnly/Secure/SameSite) y no calza con el adapter D1
de Better Auth sin fricción extra en Workers.

**Nota técnica:** se usó Web Crypto (`crypto.subtle`, `crypto.getRandomValues`)
en vez de `node:crypto`, para evitar un conflicto de tipos `Buffer` entre
`@types/node` y `@cloudflare/workers-types`, y no depender de `nodejs_compat`
para esto.

### `apps/api`
- Rutas: `POST /api/auth/signup|login|logout`, `GET /api/auth/me`.
  `signup` crea user + clinic (slug único) + membership owner +
  `clinic_settings` default + seed de 6 servicios típicos.
- CRUD mínimo por `TenantDb`: `clinic.ts`, `doctors.ts`, `services.ts`,
  `patients.ts`, `appointments.ts`.
- `secretaria.ts` migrado del fixture en memoria a D1 real (contexto público
  resuelto por sesión o por `?clinic=<slug>` — placeholder de la resolución
  por hostname que vendrá con dominios propios).
- CORS con `credentials: true` para que la cookie de sesión viaje entre
  `apps/admin`/`apps/site` (puertos distintos en dev) y `apps/api`.
- Tests reescritos contra D1 real (`@cloudflare/vitest-plugin`,
  `applyD1Migrations`), 8/8 pasando.

### `apps/admin`
- `/login` (pantalla combinada login/signup) + `RequireAuth` (guard vía
  `useMe()`) envolviendo las rutas privadas.
- `AppShell` con usuario/clínica reales (ya no `devUser` hardcodeado).
- **Sección "Landing"** nueva: editor de `clinic_settings` (nombre, tagline,
  contacto, horarios estructurados, obras sociales, FAQs y testimonios
  repetibles), guarda contra `PUT /api/clinic/settings`.
- **Onboarding**: store zustand persistido + `OnboardingTour` — popover
  anclado a elementos del nav (no modal bloqueante), 4 pasos, "Saltar"
  siempre visible, no se re-muestra si ya se completó/saltó.
- **PWA**: `vite-plugin-pwa`, manifest + service worker (`NetworkFirst` para
  `/api/`, shell precacheado). Build verificado: genera `sw.js`,
  `workbox-*.js`, `manifest.webmanifest`.
- **Voz**: `useSpeechToText`/`useTextToSpeech` (Web Speech API, `es-AR`),
  botón de mic + "leer en voz alta" por mensaje en `AssistantDock`. Si el
  navegador no soporta STT (Safari/iOS), el botón de mic no aparece —
  degrada a solo texto.

### `apps/site`
- Rebranding completo "Alvea" → "Evolución Dental" (nombre, dominio, footer,
  logo, título).
- `SignupForm.astro`: formulario real (sin React, para no romper el
  zero-JS-by-default de Astro) que llama a `POST /api/auth/signup` y
  redirige logueado al admin.

## Pendiente / bug conocido sin resolver

`pnpm --filter @dental/landing typecheck` (astro check) se queda esperando
un prompt interactivo ("¿instalar @astrojs/check?") aunque el paquete ya
está declarado como devDependency e instalado. Causa raíz encontrada: el
store de pnpm tiene una entrada rota — `@napi-rs/wasm-runtime@1.2.4`
(dependencia transitiva de `@astrojs/astro2tsx`, usado por `@astrojs/check`)
está en `pnpm-lock.yaml` pero nunca se bajó al store (`node_modules/.pnpm`).
Astro traga ese error de resolución y muestra el mensaje equivocado de
"paquete no instalado".

Se intentó `pnpm install --force` para reparar el store; se cortó a los
~10 minutos sin terminar (decisión del usuario, no fue error). **Sigue
pendiente**: terminar esa reinstalación (o `pnpm store prune` + reinstalar)
en un momento donde no estorbe, y volver a correr
`pnpm --filter @dental/landing typecheck` para confirmar que el hang
desaparece.
